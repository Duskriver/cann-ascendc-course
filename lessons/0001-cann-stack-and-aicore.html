Lesson 0001 · 零基础破冰与心智模型

初识异构计算与达芬奇 AI Core

解密 NPU 核心算力：为什么 GPU/NPU 算子不能像 CPU 一样直接写 z[i] = x[i] + y[i]？

🎯 直通实战目标 (Your Mission)： 我们最终要用 Ascend C 编写在昇腾 NPU 上跑通的高性能自定义算子。在敲下第一行代码前，你需要先看懂芯片里的“工地沙盘”：什么是算子、数据放在哪座仓库、谁负责搬砖、谁负责计算。

1. 零基础先导：什么是“算子”？为什么需要异构计算？

很多第一次接触底层开发的同学会被“异构计算”、“算子（Operator）”、“核函数（Kernel）”这三个词唬住。其实用平时写 Python/C 语言来做对比，30 秒就能彻底明白：

  • 什么是算子（Operator）？ 当你在 PyTorch 里写下一行 z = x + y（比如把两个包含 1 亿个数字的数组相加），这个“加法动作”在 AI 框架里就叫一个算子（Add 算子）。同理，矩阵相乘叫 MatMul 算子，激活函数叫 ReLU 算子。
  • 什么是核函数（Kernel）？ 算子只是一个名字，真正下发到昇腾 NPU 芯片上执行这 1 亿次加法的底层 C/C++ 函数，就叫核函数（Kernel Function）——也就是我们要用 Ascend C 编写的核心代码。

那么，为什么不直接用电脑上的 CPU 算这 1 亿次加法，非要搞一套“Host + Device 异构计算”呢？ 看下面的直观对比：

🐢 传统通用计算：CPU 单兵搬砖 平坦内存模式

CPU 就像一位博学的大学教授： 擅长复杂的逻辑判断（操作系统、网络、if-else），但手里只有寥寥几个核心。面对 1 亿次简单的加法，只能一趟趟去内存取数、算完再放回：

CPU 单核串行流水：每次算 1 对
取 x[0],y[0] ➔ 算 z[0] ➔ 取 x[1],y[1] ➔ 算 z[1] ...

代码写法： z[i] = x[i] + y[i]（直接读写同一个系统内存，简单但吞吐量低）。

🚀 异构计算：Host 指挥 + NPU 百人车间 Host + Device 协同

把不同性格的芯片组合在一起干活，就叫异构计算：让 Host（主机 CPU） 当包工头负责发号施令；把 1 亿次加法的重体力活交给拥有几十个计算车间的 Device（昇腾 NPU）：

NPU 多核 + 向量化：成千上万个数同时算！
AI Core 0: 算 [0..999] AI Core 1: 算 [1000..1999]

桥梁连接： Host 与 NPU 之间通过 PCIe / HCCS 高速跨海大桥 传输数据与指令（Kernel Launch）。

③ 🎯 CANN 算子层（Ascend C 自定义算子 —— 我们的主战场！）： 官方算子库（AOL）不可能覆盖所有前沿大模型的新结构。当遇到算子缺失或性能瓶颈时，我们就用 Ascend C 编写运行在 AI Core 上的核函数，精细控制数据搬运与并行计算！

2. 拆开达芬奇 AI Core：三大工种与“仓库 vs 工作台”

现在我们用放大镜钻进昇腾 NPU 内部。一颗昇腾芯片里整齐排列着几十个一模一样的超级计算车间，名叫 AI Core（达芬奇核心）。在每个 AI Core 车间里，有三位分工截然不同的“工人”——按他们每次处理数据的几何形状（维度），一眼就能分清：

0 维 · 单个数字 (Scalar)

Scalar 标量单元

👷 角色：车间排产调度员

每次只算 1 个单独的数。它不干大批量的张量计算，专门负责算 for 循环第几轮、下一块数据的内存地址偏了多少，并向其他单元下达指令。

单次处理：1 个标量参数
i=0 ➔ i=1
addr = base + i * 256
负责操作： 循环控制、地址指针偏移、分支跳转。
1 维 · 一整排数组 (Vector)

Vector 向量单元

⚡ 角色：高速一维流水线

每次把一整排数字（1D 向量）对齐，一条指令下去，整排元素同时完成加减乘除！是我们前几节课编写自定义算子的绝对主力。

10203040
+ 同一周期四路并发相加 ⬇️
11223344
负责算子： Add、Mul、Exp、ReLU、LayerNorm、Softmax。
2D/3D · 矩阵方块 (Cube)

Cube 矩阵单元

🧱 角色：重型矩阵压铸机

达芬奇架构的杀手锏！专攻两个二维矩阵相乘（M × K × N）。一锤子压下去，单周期直接完成 16 × 16 × 16（4096 次）乘加运算。

×
单指令整块矩阵乘加 (A × B + C)
负责算子： MatMul（全连接层 Linear、注意力 Attention、卷积 Conv）。
💡 0基础必问：为什么 Vector 工人不能直接去显存（GM）里拿数据做加法？

想象一下：Vector 计算单元是一个手速快到残影的装配工（1 秒能拧好 128 颗螺丝）。但是存放上亿颗螺丝的 Global Memory（GM 全局显存） 是一座建在几十公里外的远郊大仓库！

🏢 片外大仓库：Global Memory (GM / HBM 显存) 位于 AI Core 外部 · 所有核共享
存储容量
32 GB ~ 64 GB (极大)
读写速度
延迟数百周期 (慢)
🛠️ 片内工作台：Unified Buffer (UB 统一缓冲区) 位于 AI Core 内部 · Vector 贴身专用
存储容量
仅 ~192 KB ~ 256 KB (极小)
读写速度
单周期极速读写 (极快)

结论（硬件设计铁律）： 如果让 Vector 工人每算一个数都自己跑一趟远郊大仓库（GM），他 99% 的时间都浪费在路上！因此达芬奇架构直接从硬件电路上規定：Vector 单元只能读写手边的 UB 工作台；而远郊仓库（GM）与工作台（UB）之间拉货的苦力活，全部交给专门的物流车队——MTE（内存搬运引擎）！

3. 核心顿悟：为什么不能直接写指针？（动态数据流与代码联动）

现在我们可以彻底回答本课开头的问题了：为什么在 NPU 上写算子，不能像 CPU 一样写一行 z[i] = x[i] + y[i] 就完事？

因为在 CPU 里，硬件缓存是自动管理的；而在昇腾 AI Core 里，为了压榨出极致的吞吐性能，开发者必须亲自担任车间主任，在代码中显式指挥三个步骤：① 让 MTE2 把数据搬进 UB (CopyIn) ➔ ② 让 Vector 在 UB 里做加法 (Compute) ➔ ③ 让 MTE3 把结果写回 GM (CopyOut)。

❌ 为什么不能像 CPU 这样直接写？
zGm[i] = xGm[i] + yGm[i];
原因：xGm/yGm 在片外显存，Vector 计算单元的电路根本连不到片外！必须拆成下面三步：
✅ Ascend C 标准三段式核函数（点击代码行也可切换动画）：
// 0. 绑定片外大仓库 GM 地址指针 GlobalTensor<half> xGm, yGm, zGm;
// 1. CopyIn 阶段：指挥 MTE2 从 GM 搬入片内 UB DataCopy(xLocal, xGm, 4);
DataCopy(yLocal, yGm, 4);
// 2. Compute 阶段：指挥 Vector 在 UB 内一排同时相加 Add(zLocal, xLocal, yLocal, 4);
// 3. CopyOut 阶段：指挥 MTE3 把 UB 结果写回 GM DataCopy(zGm, zLocal, 4);
第一步 Stage 1 (CopyIn 搬入片上)： MTE2 搬运引擎启动！执行 DataCopy，将 x 和 y 的 4 个元素从片外 GM 异步拉进片上高速缓存 UB 的 xLocal 与 yLocal 槽位。

⚡ 进阶追问：既然要先搬进来、算完再搬出去，岂不是更慢了？

这是所有 0基础同学都会产生的灵魂疑问！如果只有 1 块数据，按部就班地“搬入 ➔ 计算 ➔ 写回”，确实会有等待时间。但别忘了两点：

  1. 数据切分（Tiling）： 真实大模型的张量有几百 MB，而片内 UB 只有 256 KB，所以我们一定会把大张量切成许多小块（比如块0、块1、块2...）分批处理。
  2. 三套硬件独立并行： MTE2（进货车）、Vector（计算工）、MTE3（出货车）是三个彼此独立的硬件单元！当 Vector 正在算“块0”时，MTE2 根本不用闲着，它可以同时去搬“块1”！
